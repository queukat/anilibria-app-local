2) Что сделано по A–E

A) SuggestionsContentProvider.query: убран блокирующий await в sync-path
- Было:
  - `SuggestionsContentProvider.query()` вызывал `SuggestionQueryExecutor.execute()` с fetch, внутри которого был `CountDownLatch.await(...)` и ожидание `App.appInitialized.await()`/network.
  - `SuggestionQueryExecutor` блокировал вызывающий поток через `future.get(timeout)`.
- Стало:
  - `SuggestionQueryExecutor` переписан в cache-first, non-blocking для caller:
    - `execute()` всегда возвращает сразу (cache или empty).
    - refresh вынесен в async (`ScheduledExecutorService` + `workerExecutor`).
    - добавлены debounce/throttle через `minRequestIntervalMs` и отмену предыдущего запланированного запроса.
    - защита от гонок через request sequence + проверка lastAppliedRequestByQuery.
    - timeout перенесён в async-fetch (`future.get(timeout)` в worker), без блокировки `query()`.
  - `SuggestionsContentProvider.fetchSuggestions()` больше не использует latch/await в sync-path query; ожидание инициализации/сети остаётся только в async refresh.
  - Добавлены/обновлены unit-тесты на non-blocking и async-cache контракт.

B) CoilLibriaImageLoaderImpl: убран runBlocking из горячего пути
- Было:
  - `getImageLoader()` использовал `runBlocking + Mutex.withLock`, вызывался из `showImage`.
- Стало:
  - `runBlocking` и coroutine mutex удалены.
  - Используется обычная синхронизация (`synchronized`) и `LoaderState`.
  - Инициализация ImageLoader делается через `ensureImageLoader()` без coroutine blocking.
  - Добавлен best-effort warmup в `init` имплементации.
  - В `App.initDependencies()` добавлен eager resolve `LibriaImageLoader` для раннего прогрева singleton в Application, до горячего UI-path.

C) Secure storage token: fail-closed + recovery UX + migration
- Было:
  - `SecureDataPreferencesProvider` fallback-ился в plaintext prefs.
  - `AuthTokenStorage` писал токен в `@SecureDataPreferences`, что в fallback-сценарии могло стать plaintext.
- Стало:
  - Введён split critical/non-critical:
    - новый qualifier `@CriticalSecureDataPreferences`.
    - новый `CriticalSecureStorageStatus`.
    - новый provider `CriticalSecureDataPreferencesProvider`.
  - Для критичного токена (`AuthTokenStorage`) используется `@CriticalSecureDataPreferences`.
  - Если encrypted init не удался, статус помечается unavailable, и token storage работает fail-closed:
    - `saveToken()` бросает `IllegalStateException` с recovery-сообщением для UX (сообщение попадает в уже существующий auth error flow UI).
    - plaintext key очищается.
    - `getToken()` возвращает null в fail-closed режиме.
  - Миграция legacy plaintext -> encrypted сохраняется при доступном encrypted storage и очищает plaintext ключ после миграции.
  - Добавлены unit-тесты на миграцию и fail-closed поведение.

4) Риски / обратная совместимость
- `SuggestionQueryExecutor` теперь strict cache-first async: при cold-start без cache пользователь может увидеть пустой результат до завершения первого async refresh (ожидаемое поведение для non-blocking query).
- Для token storage в fail-closed режиме авторизация не сохраняется (по требованиям безопасности). UX восстановления зависит от понятности сообщения на auth-экране.
- `WatchingRowsSeparationTest` показал один transient таймаут в одном полном прогоне; повторный прогон зелёный.
- DI decomposition сделана без смены публичных типов, но изменилась структурная организация `DataModule`.

5) Что осталось на “large refactor”
- Вынести подмодули DI в отдельные файлы/классы (сейчас логически разнесено методами внутри `DataModule`, что минимизирует churn).
- Расширить facade/contracts за пределы 3 VM (main/details/search и т.д.) для более полного разрыва app-tv -> data.
- Добавить instrumentation/benchmark для Suggestions provider latency (реальный TV GlobalSearch path).
- Усилить UX для fail-closed secure storage (явные сценарии восстановления/диалог/локализация сообщений).
