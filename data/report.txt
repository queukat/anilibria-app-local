1. Executive summary
- Репозиторий — multi-module Android-проект с двумя app-модулями (`:app-mobile`, `:app-tv`) и набором общих/data/DI/UI библиотек; глубоко анализирован только стек вне `app-mobile` (см. раздел 7).
- Критический риск безопасности: в `gradle.properties` закоммичены release-пароли/alias для TV keystore (`gradle.properties:26-29`), при этом README утверждает обратное (`README.md:16`).
- Архитектура для TV фактически двухслойная: UI (`app-tv`) часто ходит напрямую в `data` (repositories/holders/interactors), границы domain-слоя непоследовательны (`app-tv/src/main/java/...ViewModel.kt`, примеры в разделе 4).
- DI построен на кастомном Quill (Toothpick); есть явный техдолг по передаче `FragmentActivity` в DI (`app-tv/src/main/java/ru/radiationx/anilibria/di/ActivityModule.kt:11-19`).
- Асинхронщина в целом на Flow/корутинах, но есть блокирующие точки в production-пути: `CountDownLatch.await` в ContentProvider (`SuggestionsContentProvider.kt:103-113`) и `runBlocking` в image loader (`CoilLibriaImageLoaderImpl.kt:37`).
- Lint/detekt покрытие неполное и с высоким baseline-долгом: detekt отключает большинство rule set’ов (`config/detekt/detekt.yml:4-26`), baseline в `data`/`app-tv` крупный (`data/detekt-baseline.xml`, `app-tv/detekt-baseline.xml`), `media-mobile` и `app-mobile` не в `detektTargets` (`build.gradle:43-52`).
- Для secure storage используется `androidx.security:security-crypto` alpha + deprecated API (`gradle/libs.versions.toml:39`, `DataModule.kt:2,373-380`) с fallback на plaintext prefs (`DataModule.kt:383-384`).
- UI стек TV — Leanback + Fragments + ViewBinding (без Compose в анализируемых модулях по build/deps); навигация через Cicerone + custom `GuidedRouter` (`NavigationModule.kt:9-16`, `Screens.kt:40-205`).
- Тесты есть в `app-tv` и `data`, но остальные модули почти без unit coverage; smoke-тесты TV чувствительны к UI-текстам/таймингам (`AppTvSmokeTest.kt:72-88,115-128`).
- В сборке нет явных циклических project-deps (по `build.gradle` модулей), но есть «бог-слой» `:data` + «бог-модуль» DI (`DataModule.kt:168-339`).

3. Текущая архитектура (по факту)
Схема (упрощенно):
`app-tv (Fragment/ViewModel)` -> `data (repositories + interactors.tv + holders)` -> `remote/storage`.
Параллельно: `app-tv` -> `shared-app` (image/analytics/helpers), а `shared-app` сам зависит от `data`.

Ключевые артефакты:
- Entry points:
  - `Application`: `app-tv/src/main/java/ru/radiationx/anilibria/App.kt:19`
  - `MainActivity`: `app-tv/src/main/java/ru/radiationx/anilibria/screen/launcher/MainActivity.kt:22`
  - Manifest wiring: `app-tv/src/main/AndroidManifest.xml:20,30,60`
- Навигация:
  - Cicerone + guided router: `app-tv/src/main/java/ru/radiationx/anilibria/di/NavigationModule.kt:9-16`
  - Custom navigator: `app-tv/src/main/java/ru/radiationx/anilibria/common/fragment/GuidedStepNavigator.kt:18`
  - Registry экранов: `app-tv/src/main/java/ru/radiationx/anilibria/screen/Screens.kt:40-205`
- DI:
  - Root scope Toothpick: `quill-di/src/main/java/ru/radiationx/quill/Quill.kt:11-12`
  - Scope lifecycle через ViewModel: `quill-di/src/main/java/ru/radiationx/quill/QuillScopeViewModel.kt:7-13`
  - Модули app-tv: `MainActivity.kt:35-41`
- Data composition:
  - Крупный wiring: `data/src/main/java/ru/radiationx/data/di/DataModule.kt:168-339`

Нарушения/ослабления границ слоев:
- UI напрямую импортирует `data.repository.*` во множестве ViewModel (`app-tv/src/main/java/.../screen/*ViewModel.kt`, например `ProfileViewModel.kt:12`, `PlayerViewModel.kt:25-26`, `WatchingFavoritesViewModel.kt:24-25`).
- UI местами тянет `data.datasource.holders.*` (`PlayerViewModel.kt:17`, `PlayerQualityViewModel.kt:10`, `WatchingViewModel.kt:12`).
- `shared-app` зависит от `data` и использует data-провайдер в image-loader (`shared-app/build.gradle:25`, `CoilLibriaImageLoaderImpl.kt:18,27`).

6. Flow/StateFlow migration candidates
(Только кандидаты, где это дает конкретную пользу)

1) Encapsulation state в TV ViewModel
- Где:
  - `app-tv/src/main/java/ru/radiationx/anilibria/screen/watching/WatchingFavoritesViewModel.kt:45-53`
  - `app-tv/src/main/java/ru/radiationx/anilibria/screen/search/SearchViewModel.kt:27`
  - `app-tv/src/main/java/ru/radiationx/anilibria/common/BaseCardsViewModel.kt:16,19`
- Почему: публичные `MutableStateFlow/MutableSharedFlow` допускают внешний mutation и ломают single source of truth.
- Как: `private val _state = MutableStateFlow(...)`, наружу `val state: StateFlow<...> = _state.asStateFlow()`; аналогично для событий через `_events.asSharedFlow()`.

2) Lifecycle-safe collection для UI collectors
- Где:
  - `app-tv/src/main/java/ru/radiationx/anilibria/screen/profile/ProfileFragment.kt:63`
  - `app-tv/src/main/java/ru/radiationx/anilibria/screen/watching/WatchingFavoritesGridFragment.kt:145-146`
- Почему: текущие коллекции живут в `lifecycleScope`, но не ограничены `STARTED`, что ведет к лишней работе/пропускам в edge-cases.
- Как: заменить на `subscribeTo(...)` из `shared-android-ktx/.../LiveData.kt:17-37` или `flowWithLifecycle(..., STARTED)`.

3) `ApiConfig.needConfig` -> `StateFlow<Boolean>`
- Где:
  - `data/src/main/java/ru/radiationx/data/datasource/remote/address/ApiConfig.kt:23-24,35-38`
  - потребитель: `app-tv/src/main/java/ru/radiationx/anilibria/screen/launcher/AppLauncherViewModel.kt:54-67`
- Почему: сейчас смесь mutable var + `MutableSharedFlow(replay=0)` усложняет инициализацию и может приводить к missed emissions.
- Как: заменить на `MutableStateFlow<Boolean>` + единый источник истины (`needConfigState`), убрать дублирующий mutable var.

4) Упростить событийные каналы, где сейчас custom `EventFlow`
- Где: `shared-ktx/src/main/java/ru/radiationx/shared/ktx/EventFlow.kt:10-14`
- Почему: `DROP_OLDEST` + `extraBufferCapacity` могут молча терять важные события; семантика не всегда очевидна потребителям.
- Как: по сценариям выбрать `SharedFlow` (для broadcast) или `Channel` (для single-consumer events), документировать guarantees.
